        # sqlite — Конкурентность и busy_timeout

        Homework-шаблон для урока **l3_concurrency_and_busy_timeout** (Конкурентность и busy_timeout) на платформе Vibe Learn.

        ## Что делать

        На Go с modernc.org/sqlite реализуй конкурентный счётчик: таблица counter(id, value),
функция Increment(db) делает атомарный `UPDATE counter SET value = value + 1` внутри
`BEGIN IMMEDIATE`. Подготовь две конфигурации: (1) «плохую» — один пул без busy_timeout и
обычный BEGIN; (2) «хорошую» — busy_timeout=5000, WAL, BEGIN IMMEDIATE, пишущий пул
SetMaxOpenConns(1). Запусти 50 параллельных goroutine по K инкрементов в каждой. Тесты
(на файловой базе, т.к. WAL): проверяют, что в «хорошей» конфигурации итоговое value точно
равно 50*K без потерь, число ошибок SQLITE_BUSY мало/ноль, а в «плохой» — демонстрируется
рост SQLITE_BUSY. Логируй счётчик ретраев.

## Контекст (из transfer-задачи урока)

Go-сервис на modernc.org/sqlite, WAL включён. Под нагрузкой 100 RPS (смесь чтений и
записей) логи завалены `SQLITE_BUSY: database is locked`. Конфигурация: один общий пул
`db` с дефолтным числом соединений (Go ставит неограниченно), busy_timeout НЕ задан,
пишущие транзакции открываются обычным `BEGIN` (DEFERRED), а внутри транзакции код ещё
делает HTTP-запрос к платёжному провайдеру и только потом COMMIT.

**Вопрос:** разбери три отдельные проблемы в этой конфигурации и предложи по каждой
конкретное лечение:
(a) отсутствие busy_timeout;
(b) общий неограниченный пул соединений против single-writer;
(c) HTTP-вызов внутри пишущей транзакции + DEFERRED.
Затем опиши итоговую конфигурацию (PRAGMA, пулы, тип BEGIN, где делать сетевой вызов).

## Recap из урока

- `SQLITE_BUSY` / «database is locked» — сигнал «занято» из-за **single-writer**, а не повреждение. Реакция: подождать и/или причесать паттерн доступа.
- `PRAGMA busy_timeout=5000` превращает мгновенную ошибку в **ожидание-и-ретрай**. Почти обязательная настройка — но лечит не все причины.
- Главные причины блокировки: нет таймаута, **долгая читающая транзакция** (держит SHARED), **deadlock на апгрейде** (лечится `BEGIN IMMEDIATE`), длинная пишущая транзакция.
- В Go: пишущий пул `SetMaxOpenConns(1)` сериализует записи и убирает contention; отдельный читающий пул под WAL даёт конкурентные чтения.
- Single-writer — это **дизайн** SQLite, не баг. Выстраивай записи в короткую очередь; никаких сетевых вызовов внутри пишущей транзакции. В PostgreSQL же — MVCC и много писателей.

        ## Локальное окружение

        - Go 1.22+
        - SQLite встроена — **никакого сервера и docker-compose**. БД это один файл (`DATABASE_PATH`) или `:memory:` в тестах. Драйвер `modernc.org/sqlite` — чистый Go, без CGO, так что CI собирается без компилятора C.

        ## Запуск

        ```bash

        # Запустить main (создаёт схему, печатает marker; замени stub на реализацию)
        go run .

        # На файловой БД (нужно для WAL/concurrency-уроков):
        DATABASE_PATH=./app.db go run .
        ```
